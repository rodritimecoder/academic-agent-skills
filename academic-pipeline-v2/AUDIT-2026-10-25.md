# Audit — `academic/academic-pipeline-v2` — 2026-10-25

## 1. Verdict

**Wish, not skill.** `academic-pipeline-v2` is a design document dressed up as an operational skill. The directory contains only `SKILL.md` (97 lines) and `references/architecture.md` (185 lines), and the architecture doc self-declares at `references/architecture.md:3` that this is a "Draft plan (no code yet)". There are no scripts, no stage runners, no gate enforcers, and no tests. Every pipeline stage and every micro-gate exists only as prose. It is a useful specification/plan, but it cannot be executed today, so it should be marked as a draft spec until code lands.

## 2. Findings

### Critical

- **C1 — No implementation exists.** `references/architecture.md:3` says "Draft plan (no code yet)". The whole directory is only `SKILL.md` + `references/architecture.md`; there is no `scripts/`, no `05_verify/` gate runner, no `step_*.json`, no tests.
  - *Why it matters:* A "run" of this skill is impossible. All five stages and their gates are narrative; nothing exits non-zero or produces `step_NN.json` as `SKILL.md:29` and `SKILL.md:92-97` promise.
  - *Fix:* Add a real runner (`scripts/run_pipeline.py` or per-stage scripts) and mark the skill `status: draft` in frontmatter until it executes end-to-end.

- **C2 — `allowed-tools` blocks the stages the SKILL itself names.** `SKILL.md:10` allows only `Bash(canvas-cli:*) Bash(zoom-recorder:*) Bash(markitdown:*) Bash(jev:*) Read Write`. Stage 2 requires `openrouter-free`, `free-swarm`, and `semantic-cache` (`SKILL.md:76`); Stage 3 requires `okf-architect`, `state-compactor`, and `cgate` (`SKILL.md:84-85`); Stage 5 uses `jev-decision` (covered by `jev:`, but only as an alias).
  - *Why it matters:* An agent following this skill literally cannot invoke the tools the pipeline says it uses. The skill contradicts its own tool budget.
  - *Fix:* Expand `allowed-tools` to exactly the tools the final implementation uses (e.g. add `Bash(okf:*)`, `Bash(state-compactor:*)`, `Bash(cgate:*)`, `Bash(openrouter-free:*)`, `Bash(eval-router:*)`), or delete the unallowed tools from the prose.

- **C3 — `free-swarm` is named but does not exist.** Referenced at `SKILL.md:5`, `SKILL.md:76`, `references/architecture.md:115`, `references/architecture.md:127`, and `references/architecture.md:152`. There is no `glitch-cat/free-swarm` directory and no `free-swarm` entry in `cli-manifest.json`.
  - *Why it matters:* The parallel fan-out stage is unbuildable as specified; the "majority vote across nine zero-cost subagents" mechanism has no backing skill.
  - *Fix:* Replace `free-swarm` with an existing mechanism (`openrouter-free` subagents, `subagent-spaces`, or `swarm-dispatch`) or create the missing skill before referencing it.

- **C4 — `semantic-cache` is named but not a CLI command.** `SKILL.md:76` says classifiers are "cached via `semantic-cache`", but `cli-manifest.json` contains no `semantic-cache` command.
  - *Why it matters:* As written, the cache layer cannot be invoked the way the prose implies.
  - *Fix:* Register a `semantic-cache` CLI entry in `cli-manifest.json`, or reword to an importable library and add the import path.

### Major

- **M1 — "Supersedes v1" is premature.** `SKILL.md:8` and `SKILL.md:17` claim v2 supersedes `academic-icm`, but v1 is still the only implementation in the repo: `academic/academic-icm/scripts/academic_icm.py` is 112 KB and is the only registered `academic-icm` command target in `cli-manifest.json`; v2 has no target and no command entry.
  - *Why it matters:* Any router that trusts `Supersedes` prose and swaps in v2 will get nothing executable; v1 users are sent to a non-implementation.
  - *Fix:* Keep v1 as the live skill until v2 passes its own gates, or remove the supersede claim and label v2 `experimental`/`draft`.

- **M2 — v1 has 14 Python files but no tests.** `academic/academic-icm` contains 14 `.py` files (including `scripts/academic_icm.py` and `modules/graph-memory/graph_memory.py`) and no `tests/` directory. Since v2 plans to port v1's graph/Anki UI (`references/architecture.md:24-28`), there are no regression tests to protect those ports.
  - *Why it matters:* The v2 render stage ("reuse the Anki UI from old `viz.html`", "port graph functions from old `viz.html`") has no safety net; the planned reuse of a 112 KB untested monolith is high-risk.
  - *Fix:* Before porting, add characterization tests for v1's graph + Anki behavior; require v2's render stage to pass them.

- **M3 — Port :8080 and :8083 assumptions are unverified and hardcoded.** `SKILL.md:9` declares compatibility with "local inference (:8080, :8083)" and `references/architecture.md:63` assumes a "local 27B classifier on the GPUs", but the skill never checks those services and provides no fallback for their absence. `cli-manifest.json` registers `local-llm` only as a client, not as a health check the pipeline runs.
  - *Why it matters:* Stage 2/Stage 5 gates depend on models; if ports are down the whole pipeline dies with no `step_NN.json` evidence (contradicting the "always run the control" promise).
  - *Fix:* Add a Stage 0 preflight that `curl`/`nc`-checks :8080 and :8083 and serializes the result, or make model-dependent stages degrade to deterministic code with evidence.

- **M4 — Stage 2 claims a local 27B classifier, but repo evidence points to a 35B local model.** `references/architecture.md:63` says "local 27B classifier", while `cli-manifest.json` (`local-llm` description) advertises "Qwen3.6-35B-A3B ... on port 8080". `references/architecture.md:115` later says "27B/local 35B".
  - *Why it matters:* The plan is internally inconsistent about the local model, which will cause the wrong resource/VRAM decisions and wrong prompt sizing when implemented.
  - *Fix:* Pick one model and port (and its VRAM budget) and reference it everywhere.

- **M5 — `eval-router` is named as a headline dependency but has no CLI tool entry aligned with the prose.** `references/architecture.md:110` describes `eval-router` as "self-calibrating request router"; `cli-manifest.json` only maps `eval-router` to `glitch-cat/eval-router/eval_router.py`. Stage 2 never says how it is called.
  - *Why it matters:* Without an invocation contract, the promised routing + speculative shadow eval cannot be implemented against the real CLI.
  - *Fix:* Add the `eval-router` invocation (subcommand + flags) to Stage 2 and confirm `eval_router.py` actually accepts those flags.

### Minor

- **m1 — Frontmatter lacks status/version.** `SKILL.md:1-11` has `name`, `description`, `compatibility`, `allowed-tools`, but no `status: draft` or `version`, so tooling cannot distinguish this from a runnable skill.
  - *Fix:* Add `status: draft` and `version: 0.1-draft`; flip to `status: live` only when gates exist.

- **m2 — Stage folder schema drifts between the two docs.** `SKILL.md:48-52` puts `01_weeks/`, `02_index/`, `03_state/` under `03_structure/`; `references/architecture.md:82-89` puts them at the course root (`<course>/01_weeks/...`) with `_templates/` added.
  - *Fix:* Choose one layout (course root is the OKF v0.2 convention per `references/architecture.md:82-89`) and make `SKILL.md:33-61` match it.

- **m3 — `tailscale serve` is named without a tool alias.** `SKILL.md:90` says HTML "can be ... exposed via `tailscale serve`", but `allowed-tools` has no `Bash(tailscale:*)` (only `tailscale-ops` exists in `cli-manifest.json`, not `tailscale`).
  - *Fix:* Either drop the sentence or add the correct `tailscale-ops` invocation to `allowed-tools`.

- **m4 — `zoom-recorder` is referenced in `allowed-tools` and Stage 1, but the manifest target only exists as a download script.** `cli-manifest.json` maps `zoom-recorder` to `academic/zoom-recorder/scripts/zoom_download.py`; there is no evidence in this skill of the "keyframes only, never full video" mode the plan requires (`references/architecture.md:51`).
  - *Fix:* Verify `zoom_download.py` actually supports transcript/keyframe-only fetching; if not, that is a blocking gap for Stage 1, not a documentation nit.

- **m5 — `allowed-tools` uses `Bash(markitdown:*)` but the manifest exposes both `markitdown` and `markitdown-cli`.** `SKILL.md:10` permits `markitdown:`, while the manifest has a separate `markitdown-cli` alias. Minor, but the alias inconsistency invites "tool not found" failures.
  - *Fix:* Use the exact `markitdown-cli` alias in `allowed-tools` (as Stage 1's prose does).

- **m6 — The `AGENTS.md` root routing file is described but no template is shipped.** `SKILL.md:37` promises `< 60 lines` routing; `references/architecture.md:82-89` mentions `AGENTS.md` rules but no `_templates/` exists in the skill directory.
  - *Fix:* Ship `_templates/AGENTS.md` and per-stage `CONTEXT.md` templates so the workspace can actually be scaffolded.
